## 3. The five strongest things

1. **Dedupe and reparse are now one code path, applied when the ledger is written.** `_processPending` (`sqlite_finance_repository.dart:190`) is the only writer, `ingest` and `_reparse` both call it, and `_reconcileDuplicates` applies the same `DedupeEngine` to the stored rows inside the same pass. "Reparse is identical to a fresh scan" is therefore not a claim, it is the call graph — and it is what makes `reparseAll()` on a `parser_version` bump safe to run automatically. That is the single biggest architectural win of the round.
2. **The money-in taxonomy is honest at the UI boundary.** `MoneyInKind` is persisted (schema v9), `isTrueIncome` is the only thing that may reach "Came in" (`monthly_summary.dart:226`), and — the part that matters — Home now *refuses to answer* when the inbox contains no true income: it shows "Out this month" + "Bills due" and the screen-reader sentence says "No income messages found, so there is no left over figure" (`home_screen.dart:241-250, 297`). On the owner's real inbox that is the correct answer (0 salary, 0 interest, ₹1.59 L of P2P receipts). Fabricating a savings rate would have been worse than saying nothing.
3. **Card identity is gated on card wording, not on "has four digits".** `_extractCardLast4` (`transaction_extractor.dart:600`) requires a card context or a card issuer, with an explicit `_accountContext` escape hatch so an SBI Card header reporting `A/c XX1234` stays a deposit account. Measured effect on the owner's inbox: 21 cards/0 limits/126 non-card `card_key` rows → **4 cards/1 limit/32 non-card rows**, plus a learned limit from an `Avl Limit` alert, plus `deleteCard` and a self-healing `_cleanupPhantomCards` so a phantom is both preventable and removable. The remaining two gaps (a wallet still mints one; `instrument` is not part of the gate) are narrow now, not systemic.
4. **Bill notices finally exist, and they are parseable evidence rather than a guess.** `billNotice` runs for every message, not just transactions (`:284`), so informational statement SMS now populate `card_bills` (6 rows on the real inbox, was 0). I checked three of them against their raw SMS by hand — total due, minimum due, due date and statement date all exact — and the schema collapses statement + reminder duplicates through a unique index (`app_database.dart:184-197`) so one statement cannot double the "still due" figure.
5. **The measurement culture is real and it caught its own regression.** `flutter analyze lib` clean, 240/240, 109/109 corpus, a replay harness that reproduces HEAD, and — critically — a shipped database that now *agrees* with the replay (₹3,12,407.81 vs ₹3,12,408). Round 1 had to distrust the artifact. This round the numbers in `CLAUDE.md` are reproducible, including the one regression the owner would never have found by hand (`phishing` 151 → 2). The gaps I raise in §4 are gaps in the *scope* of the measurement, not in its honesty.

### B. Blockers that remain, worst first

#### B1 (round 1's R1-B2/R1-B4/R1-B5) — The real-time path is still not wired: a captured SMS is never parsed on open, and the notification's category choice is deleted before it can apply. **High.**
`AppState.init()` ingests only when `_data.transactions.isEmpty` (`app_state.dart:75-77`); `refresh()` loads without ingesting (`:86-95`); no `WidgetsBindingObserver` exists anywhere in `lib/`. So the receiver's core promise — "the message is stored and appears next time" — only happens if the user taps Scan or pulls to refresh, and README:31 ("the payment is already categorised when you next open the app") is false for the only situation in which the notification is actionable, i.e. the app was closed.
Worse, the ordering bug round 1 found is untouched: `load()` calls `_applyPendingCategories` **first** (`sqlite_finance_repository.dart:66`) and that method applies, then `DELETE`s the whole queue unconditionally (`:1283`). At cold start the transaction does not exist yet (`UPDATE … WHERE dedupe_key = 'sms:<ref>'` matches 0 rows), so the user's tap is destroyed and the row later appears with the rule category instead. Meanwhile `onReceive` still has no `try/catch` (`TransactionSmsReceiver.kt:32-45`), so one bad SQLite call loses the message entirely — now with `onOpen` DDL making a throw marginally more likely.
**Fix:** ingest when `SELECT COUNT(*) FROM sms_messages WHERE processed = 0 > 0` on init *and* on `AppLifecycleState.resumed`; move `_applyPendingCategories` after the ingest and delete only rows whose `UPDATE` reported > 0 changes; wrap `RawSmsStore`/`NativeSmsParser`/notification in `try/catch`. Then add the one repository test with a fake store that round 1 also asked for — this is the layer where none of the current 240 tests look.

#### B2 — One card-bill payment is counted twice in "Out this month", and the tool that certifies P2 cannot see it. **High (P2 violation).**
Proof, §6.5: the HDFC bank-side alert ("PAYMENT OF Rs. 3772.00 RECEIVED TOWARDS YOUR CREDIT CARD ENDING WITH 6859", 18 Oct 07:47) and the issuer-side alert ("Online Payment of Rs.3772 … credited to your card ending 6859", 19 Oct 08:21) are the *same* payment. Both parse as `transfer / creditCardBill`; `DedupeEngine` never compares them because `windowSeconds = 180` (`dedupe_engine.dart:19`) and they are 20 h apart. Both then feed `cardBillPaymentPaise` and `moneyOutPaise = spend + cash + cardBills` (`monthly_summary.dart:76,233-237`), so one ₹3,772 payment becomes ₹7,544. On this inbox the pattern repeats six times (₹5,861 / ₹7,683 / ₹13,037 / ₹5,552 / ₹8,592 / ₹3,772) — **₹44,497 of the ₹1,37,762 card-bill total, 32 %, is double counted in the hero figure.** The reason nobody caught it: `measure_inbox.py` certifies P2 with a **10-minute** bucket grouped by merchant, and both legs have no merchant, so "0 duplicate groups" is true and useless.
This is not the same bug as round 1 (that one *deleted* a real payment); it is the mirror image, and it is the number the owner reads first.
**Fix:** pair card-bill legs explicitly — same amount, both `creditCardBill`, any sender, window ~48 h, and skip the merge when a `referenceId` distinguishes them — and merge them in the engine, not by widening the general window. Then extend `measure_inbox.py` to the same rule so the certificate covers what the engine claims.

#### B3 — When the pair *is* inside the window the wrong survivor wins, and the payment disappears from the card. **High.**
Proof, §6.6: the SBI debit (`A/C X4642 debited by 72570.85 … trf to PhonePe`, 17 Jul 07:27:18) and the Axis credit (`Payment of INR 72570.85 has been received towards your Axis Bank Credit Card XX5365`, 07:28:05) are 47 s apart, so they merge — correctly. But `_richer` scores the SBI row higher (it has a merchant string), so the survivor is `kind=transfer, transfer_reason=none, cardKey=null, instrument=wallet` and the Axis row is **deleted**. Consequence: the ₹72,570.85 payment is invisible to the Axis card, `billDuePaise` cannot net it off, and a paid ₹72,570 bill keeps showing as due — the exact failure the Cards tab exists to prevent, produced by the dedupe fix itself.
It is also the same root cause as B2: the bank-side leg loses its `cardKey` because `_extractCardLast4` cannot bind "credit card ending with NNNN" (`_cardContext`'s first alternative `credit\s*card` wins and the tail starts after "card", at " ENDING WITH 6859" — `transaction_extractor.dart:639-644`; `_extractLast4` succeeds here only because it also scans `_maskContext` matches, which include `ending with`). So the fix is one regex ordering bug plus a rule about which leg must survive: **when one leg carries `cardKey`/`creditCardBill` and the other does not, the card-aware leg must win.**
Note the corpus cannot catch this: 109/109 passes while the fixture H07 asserts `instrument: creditCard` for a bank-account debit and never asserts `cardKey` (`sms_corpus_test.dart:195` is the only tail assertion).

#### B4 — "Just this payment" permanently suppresses future payments, and the app says otherwise. **High (silent data loss).**
The inbox detail sheet offers two scopes — "Just this payment" and "Every payment from X" (`inbox_detail_sheet.dart:413-430`) — and the first closes with "Removed this payment from your totals" (`:204`). But `markNotTransaction(everyFromMerchant: false)` calls `excludeTxn(txnKey)`, and `excludeTxn` **always** writes an `excluded_shapes` row keyed `sender|merchant|amount-band` (`sqlite_finance_repository.dart:784-802`). `_processPending` consults that set before writing any row (`:229`), so the rule suppresses all *future* matching payments.
The band is wide: §6.4 shows ₹408.00 and ₹417.00 Pluxee charges produce the identical key `pluxee|pluxee meal|100-500`. On this inbox, one "not a transaction" tap on a ₹408 Swiggy meal-card charge would silently swallow every Pluxee charge between ₹100 and ₹500 from then on — several per month — with only a `hits` counter as evidence (`excluded_shapes.hits`). The behaviour is deliberate in the key design (`test/learning_loop_test.dart:101` asserts the band collapse); what is wrong is that a UI scope called "just this" triggers it.
**Fix:** `markNotTransaction(everyFromMerchant: false)` must delete the row and *not* write a shape — or the sheet must say "Never count payments like this again" and offer one scope. Add a repository test that asserts `excluded_shapes` is empty after a single-payment exclusion.

#### B5 — The reparse is a destructive rebuild with no transaction and no staging, and it is now the normal upgrade path. **High (data safety).**
`_reparse` does `DELETE FROM transactions WHERE source_type != 'manual'` and then reinserts row by row (`sqlite_finance_repository.dart:393-397`, `:246`), wiping `card_bills` and resetting every `sms_messages.processed = 0`. It runs automatically from `load()` when `parser_version` or `schema_version` differs (`:69`, `:439-459`). If the process dies in the middle — phone low on memory, user swipes away — the ledger is partly rebuilt and the app shows an empty dashboard with "Something went wrong reading your messages". Recovery is automatic on the next launch (because `_writeParserVersion` is last), but the intermediate state is a ledger that is neither old nor new, and nothing in the UI says a rebuild is happening. It also *blocks the first frame*: 2 000 messages → ~2 000 `UPDATE`s + 282 inserts run before Home draws.
**Fix:** rebuild into `transactions_new` and `ALTER TABLE … RENAME` in one transaction (sqflite supports `db.transaction`), or at minimum delete-and-rebuild inside one transaction so a kill rolls back, plus a "Reparsing your messages" progress state. This is the only remaining place where a user's ledger can be temporarily absent.

#### B6 — "To confirm" money still moves the month's total. **Medium-high.**
Unchanged from round 1 except for the cap. Proven in §6.1: a 12,340-paise `needsReview` row is `isCountable` (`txn_guards.dart:15-29` never looks at `needsReview`), so `SummaryCalculator` counts it (`finance_repository.dart:260`). ARCHITECTURE:60 explicitly promises the opposite ("This is why the parser can be imperfect without the totals being wrong in a hidden way"), which makes this the sharpest doc-vs-code contradiction in the repo. Real-data exposure is now small (one ₹2,249 spend row of ₹3.12 L) because review rows are mostly SIPs and `debit by transfer` transfers, so severity is lower than round 1 — but the *rule* is still wrong, and the research memo's tiered admission (ASSERTED visible, not counted) is still unimplemented.
**Fix:** `isCountable` returns false (for totals only) when `needsReview`; keep the row visible in the list and add it to the total when the user confirms. One line plus a test, and it makes the review queue mean something.

#### B7 — A stale bill still says "due" forever. **Medium.**
Unchanged; §6.2 reproduces round 1's exact numbers (`daysToDue = −526`, `dueSoon = true`) because the roll-forward stops at 12 months (`card_metrics.dart:412-419`) and `dueSoon` has no lower bound (`:210`). Now it *matters more* than in round 1: `billNotice` works, so there are 6 bills in the DB and any card that stops sending statements keeps a two-year-old "Bill due" warning on Home forever.
**Fix:** ignore a bill whose statement is older than ~60 days, and require `daysToDue >= 0` in `dueSoon`. Two lines, one test.

#### B8 — `MoneyInKind.other` is unreachable, and no inflow can be reclassified. **Medium.**
Every credit that is not card-payment/redemption/refund/cashback/salary/interest/wallet/P2P falls through to `MoneyInKind.selfTransfer` (`transaction_extractor.dart:522`) — including a silent and deliberate fallback with no way for the user to disagree: `txn_detail_sheet.dart` offers categories only, so `TxnKind` and `MoneyInKind` are immutable after ingest. A business receipt, stipend or bonus is therefore permanently "Between your own accounts", and `Income` can never be reached for it. `other` (documented as "a genuine income credit whose source we cannot name", `enums.dart:42`) is dead code.
**Fix:** either delete `other` or route the anonymous-credit fallback to it; and add one action — "This was income" — that sets `money_in_kind` (and `kind`) on a row and teaches the sender. `CLAUDE.md` already lists "allow marking an inflow as salary once", which is the same fix.

#### B9 — A wallet is still a credit card in the Cards tab. **Medium.**
`Card|6719` (Pluxee Meal Card) is one of the 4 cards in the shipped DB, created because `_ensureCard` runs for every row with a `cardKey` (`sqlite_finance_repository.dart:264`) and `_extractCardLast4` matches "Pluxee Meal Card wallet, card no.xx6719". Its 26 wallet spends (₹8,357) are attributed as credit-card spending because `card_metrics` keys on `cardKey` alone (`card_metrics.dart:329`), so the Cards tab shows a prepaid meal wallet with utilisation, a statement cycle and a "bill due" concept. The code comment two lines above claims "Only a *card* key may mint a card … an `A/c XX1234` can no longer become a phantom credit card" — true for accounts, false for wallets.
**Fix:** gate `_ensureCard` on `instrument == creditCard || transferReason == creditCardBill || billNotice`, and gate `card_metrics` attribution the same way. This is a two-line change that finishes round 1's B3.

#### B10 — Documentation is still load-bearing and still wrong in five places. **Medium.**
Repo-wide `flutter analyze` exits 1 (27 info lints) while README:71 says "zero issues expected" — the round-1 finding, unfixed and one worse. README:47 and ARCHITECTURE:56 still describe "different sender … marked, never deleted" for a rule that permits same-sender merges and deletes the loser (`duplicate_of` is 0 in every DB). ARCHITECTURE:60 still promises needs-reviewed money does not move totals. ARCHITECTURE:68 and `app_database.dart:56` still say WAL (`journal_mode = delete`). README:42 says "one parser" while `NativeSmsParser.kt` ships. README:43 says "~90 codes" against 72. `CLAUDE.md` — now the most-trusted document in the repo — repeats two: "4 real cards (… Pluxee)" and "111/111" (it is 109/109).
**Fix:** make the docs derive from the code where possible (the corpus count and the card list are both one command away), and delete the two safety claims that are no longer true rather than rewording them. A `docs/` claim that a reviewer can disprove in one query costs more trust than the feature earns.

#### B11 — The P2 certificate is scoped more narrowly than the guarantee. **Medium-high; this is the meta-blocker.**
README and `CLAUDE.md` both assert "P2: never double count — 0 duplicate groups", certified by `measure_inbox.py`. That check groups by amount + merchant + sender inside a **10-minute** bucket. B2 shows the commonest real duplicate (bank + issuer for one card payment) is ~20 h apart and has no merchant on either leg, so it is invisible by construction. Similarly `replay_inbox.dart` certifies "other = 0.7 % of spend" but re-implements the pipeline rather than calling it, ignores learned rules and exclusions, and cannot see the DB effect of `_reconcileDuplicates` deletions.
An owner requirement is only met if the *measurement* would fail when the property fails. Today, three of the four measured guarantees (P2, other-share, duplicate groups) are measured by tools that share the engine's assumptions.
**Fix:** make `replay_inbox.dart` call the repository's own `_processPending` path (or expose it), and re-implement each `measure_inbox.py` check from the *guarantee's wording* ("one real payment must yield exactly one ledger row") rather than from the engine's window. Concretely: add a check that counts rows sharing (amount, `creditCardBill`) within 48 h and fails if > 1.

## 6. Three changes with the best score-per-hour

### 1. Make one real card-bill payment produce exactly one ledger row, and let the card-aware leg win (≈3–4 h; E2 +1.0, E5 +0.3, E6 +0.2)
- Add a card-bill pairing rule to `DedupeEngine`: same amount, both `TransferReason.creditCardBill`, **any** sender, window ~48 h, skip when `_refsDistinguish`; merge them and keep the leg with `cardKey` (extend `_score` so `cardKey` outranks a merchant string, or special-case the winner for bill pairs).
- Fix the root cause: in `_extractCardLast4`, prefer the `card … ending/no./with` alternative over the bare `credit\s*card` one (or fall back to `_extractLast4` whenever a card context exists and no `_accountContext` does), so the bank-side HDFC alert binds `6859` like the issuer side already does.
- Add the missing corpus assertions: `cardKey` for H07-style bill payments and for "credit card ending with NNNN", plus a `Duplicate pairs` fixture for the 20-hour bank/issuer pair.
- Re-derive `measure_inbox.py`'s P2 check from the guarantee ("one payment ⇒ one row", 48 h, amount + `credit_card_bill`) so the certificate can fail.
**Why first:** it removes a 32 % overstatement from the number the owner reads first ("Out this month"), it fixes a paid bill showing as due, and it is the only finding in this report that makes a *claimed, measured* guarantee false.

### 2. Wire the real-time path and stop deleting user choices (≈3–4 h; E4 +0.8, E5 +0.3, E1 +0.2)
- `AppState`: ingest on init when unprocessed messages exist, and on `AppLifecycleState.resumed` behind a `WidgetsBindingObserver`; keep the cheap `WHERE processed = 0` count as the guard.
- Move `_applyPendingCategories` after the ingest in `load()` and delete only the rows whose `UPDATE` changed something (`rawUpdate` returns the affected count) — the notification category then actually lands.
- Wrap `RawSmsStore` construction, `insertSms`, the preview parse and the notification in `try/catch` in `TransactionSmsReceiver.onReceive`; a lost notification is acceptable, a lost SMS is not.
- Make "Just this payment" not write an `excluded_shapes` row (B4), or relabel the action to match what it does.
- Add the first repository test with an in-memory fake store: capture → ingest → pending category applied; and one that asserts `excluded_shapes` is empty after a single-row exclusion.
**Why second:** it converts two README promises ("captured in real time", "already categorised") from marketing into behaviour, and it closes the only remaining *silent* data-loss paths — a swallowed notification choice and a future-suppressing negative rule.

### 3. Make the reparse transactional and "to confirm" money inert (≈2–3 h; E5 +0.6, E2 +0.3, E6 +0.2)
- Rebuild `transactions` into a shadow table and `ALTER TABLE … RENAME` inside one `db.transaction`, so a kill rolls back instead of leaving half a ledger; surface a "Reparsing messages" state while it runs.
- `TxnGuards.isCountable`: return false when `needsReview` (visible, not counted); count it the moment the user confirms. This makes ARCHITECTURE:60 true instead of deleting it.
- Fix `dueSoon`/stale bills (B7) in the same pass — it is now user-visible because bill notices work.
- Update the five false doc claims in one commit, and generate the two numbers `CLAUDE.md` currently gets wrong (card count, corpus size) from a command instead of by hand.
**Why third:** it removes the last window in which a user can open the app and find no ledger, makes the review queue honest, and stops the documentation from being the weakest part of an otherwise well-measured project.

**Next three (after these):** gate `_ensureCard`/card attribution on `instrument` so a meal wallet stops being a plastic (B9); give `MoneyInKind` a user override and either kill `other` or route the anonymous-credit fallback to it (B8); add the 10 missing sender entity codes and a `classifier_diagnostics` reason column so a rejected row is explainable (B11-round-1 residue + B9-round-1 residue).
